MARVEL CARD VAULT: SOLDGRAPH SIDE KICK LIMIT + VALUE SCOUT ACHIEVEMENT

We are adjusting the SoldGraph user-access strategy.

Do not publish yet.

Do not change the broader hybrid pricing architecture.

==================================================
PRODUCT DECISION
==================================================

SIDE KICK:

Allow 20 TOTAL provider-consuming SoldGraph Market Price refreshes over the lifetime of the account.

After the 20th actual provider-consuming refresh:

- do not make another SoldGraph call for that Side Kick user
- continue showing cached pricing
- continue showing the existing eBay baseline where appropriate
- when they attempt another real SoldGraph refresh, present the existing SUPER_HERO upgrade experience

IMPORTANT:

Do NOT show users:
- "20 refreshes"
- "X remaining"
- a counter
- SoldGraph terminology
- API limits
- credits

This is a quiet product limit.

SUPER_HERO:

NO USER-LEVEL SOLDGRAPH REFRESH LIMIT.

Do not implement:
- daily limit
- monthly limit
- lifetime limit

SUPER_HERO should effectively have unlimited Check Value usage from the collector's perspective.

However, SUPER_HERO requests MUST still respect:

- SoldGraph shared global quota
- global safety reserve
- card cache TTL
- same-card refresh cooldown
- concurrent request deduplication
- abuse / endpoint rate protection

"Unlimited" means no subscription entitlement cap. It does NOT mean bypassing provider-level safety controls.

==================================================
WHAT COUNTS TOWARD SIDE KICK'S 20
==================================================

Increment the Side Kick lifetime refresh count ONLY when:

1. user explicitly requests Check Value / refresh
2. there is no sufficiently fresh SoldGraph result that can satisfy the request
3. the shared lock determines this request is actually responsible for the provider lookup
4. MCV actually initiates a new SoldGraph search

Do NOT count:

- normal price views
- cached SoldGraph results
- cached eBay results
- page loads
- same-card requests fulfilled from cache
- requests deduplicated behind another user's/in-flight provider request
- requests blocked before SoldGraph is called
- background eBay pricing
- admin/operator pricing work

==================================================
FAILED PROVIDER CALLS
==================================================

Inspect the existing provider-client behavior.

Prefer to increment the lifetime allowance when an actual SoldGraph search has consumed provider quota.

If SoldGraph rejects the call before consuming a search credit, do not consume the user's allowance.

If provider usage cannot be reliably distinguished:

use the safest server-side interpretation and document it.

Never increment from the frontend.

==================================================
PERSISTENT ACCOUNTING
==================================================

The Side Kick lifetime count must be durable.

Use the existing database and user/account architecture.

Do not store this only:
- in memory
- localStorage
- browser state
- mobile state

Use an appropriate durable field/table/event.

Before creating a new table, inspect whether an existing:
- usage
- entitlement
- event
- xp_events
- account metadata

structure is appropriate.

Do not overload XP data if it creates poor architecture.

We need to reliably answer:

"How many provider-consuming Market Price refreshes has this Side Kick account used?"

Across:
- web
- iOS
- Android
- logouts
- devices
- server instances

==================================================
SUPER_HERO BEHAVIOR
==================================================

SUPER_HERO users:
